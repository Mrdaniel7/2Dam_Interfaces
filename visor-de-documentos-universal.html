1. Funcionalidades (qué hace la app)

1.1 Lista de funcionalidades

  • IDE tipo “pro”: header con acciones, pestañas (tabs), sidebar y panel central de trabajo.
  • Abrir archivos locales (multi-select) y tratarlos como pestañas editables.
  • Persistencia real: guarda archivos/estado en IndexedDB + restaura sesión (tabs abiertos) desde localStorage.
  • Temas Dark/Light con variables CSS y toggle inmediato.
  • Markdown pro: editor Monaco + preview en vivo + split view redimensionable + sincronización de scroll.
  • HTML pro: editor Monaco + preview con <iframe> + split view + botón “Actualizar”.
  • Editor de código (Monaco) con consola integrada y botón “Run”.
  • Ejecución:
    • JavaScript en local (eval controlado en consola).
    • Python/Java/C++ vía Piston API (cloud compile/run).
  • PDF: visor por páginas (PDF.js) + modo mano/dibujo/texto para anotaciones.
  • Export PDF con anotaciones (PDF-Lib): hornea textos/dibujos encima del PDF.
  • DOCX: visor (docx-preview) + botón “Editar” para pasar a editor tipo Word (Quill).
  • ODT: visor “alta fidelidad” leyendo content.xml (JSZip) + botón “Editar” (Quill).
  • XLSX/CSV: visor rápido (Sheet → HTML).
  • Imágenes y multimedia: visor simple para png/jpg/webp y audio/video.
  • Paleta de comandos (Ctrl+K) + acciones según contexto (con o sin tab activo).
  • Atajos: modal de ayuda con shortcuts.
  • Drafts: crear archivos de ejemplo (MD/HTML/JS/PY/Java) con demos y snippets “bonitos”.
  • Zoom de editor (Ctrl + rueda) para Monaco + indicador flotante.
  • PWA mínima: manifest + service worker inyectado (instalable).

Extracto clave: “fábrica” que decide qué visor/editor usar

static async createViewer(file) {
  const ext = file.name.split('.').pop().toLowerCase();

  if(['md','markdown'].includes(ext)) return this.createMarkdownView(file);
  if(['html'].includes(ext)) return this.createHtmlView(file);

  const codeExts = ['js','css','py','json','txt','java','cpp','c','h','xml','sql','php','go','rs','cs','ts'];
  if(codeExts.includes(ext)) return this.createCodeView(file, ext);

  if(file.contentRef && (ext === 'docx' || ext === 'odt')) return this.createOfficeEditor(file, ext);

  if(ext === 'docx') return this.createDocxViewer(file);
  if(ext === 'odt')  return this.createOdtViewer(file);
  if(['xlsx','csv'].includes(ext)) return this.createXlsxView(file);
  if(['pdf'].includes(ext)) return this.createPdfView(file);

  const imgExts = ['png','jpg','jpeg','gif','svg','webp'];
  if(imgExts.includes(ext)) return this.createImageView(file);

  const mediaExts = ['mp3','wav','mp4','webm','ogg'];
  if(mediaExts.includes(ext)) return this.createMediaView(file, ext);

  return this.createHexView(file);
}

Qué hace este código (muy breve):

  • Detecta la extensión del archivo abierto.
  • Enruta a un visor/editor especializado (Markdown, HTML, Code, PDF, Office…).
  • Si hay contenido editado (contentRef), prioriza el modo editor.

2. Versiones 1–5: descubrimiento + prompts largos

2.1 Resumen de prompts (ciclos 1–5)

  • Arranqué con un prompt inicial describiendo la app y pedí a la IA que hiciera preguntas hasta que yo dijera explícitamente “PARA”, para terminar con un prompt completo.
  • Metí ese prompt en Codex, pero el resultado no me gustaba estéticamente y sentí que la solución era demasiado “genérica”.
  • Copié el chat completo (preguntas + respuestas) y lo pasé por otra IA para que me generase un esquema de funcionalidades (lista clara de “todo lo que quiero”).
  • Intenté varios ciclos de “código actual + descripción + qué falta + genera prompt”, pero al meter prompts enormes la IA perdía contexto y rompía cosas.
  • Decidí priorizar un enfoque: empezar simple y crecer por iteraciones, en vez de pedir “todo a la vez”.

3. Versiones 6–12: esquema de funcionalidades + checklist

3.1 Resumen de prompts

  • Convertí el chat inicial en una descripción funcional (tipo “especificación”) para no olvidarme nada.
  • Flujo repetido: (1) código actual + (2) descripción → “dime qué falta” → “genera un prompt concreto”.
  • Detecté el problema: cuando el prompt mezclaba demasiadas features, la IA se desorientaba y rompía la UX o la estructura.
  • Decidí dividir por bloques: primero editor y persistencia, luego visores, luego exportación y detalles pro.
  • Desde aquí, casi todo se construyó con mini-prompts (muy pequeños) en vez de “mega-prompts”.

Extracto clave: guardar y restaurar sesión

saveSession() {
  localStorage.setItem('hacker_session_v2',
    JSON.stringify(this.openTabs.map(t => t.id))
  );
}

async restoreSession() {
  const sessionIds = JSON.parse(localStorage.getItem('hacker_session_v2') || '[]');
  for (const id of sessionIds) {
    const file = await FileSystem.getFile(id);
    if (file) this.openTabs.push(file);
  }
  if (this.openTabs.length > 0) this.activateTab(this.openTabs[0].id);
}

Qué hace este código:

  • Recuerda qué tabs estaban abiertas.
  • Reabre el estado al recargar (experiencia tipo app real).

4.1 Resumen de prompts

  • Empecé a hacer prompts muy pequeños y concretos, usando la función de “marcar espacio” para que cada cambio fuera controlado.

Extracto clave: carga de Monaco (sin romper AMD)

static async loadMonaco() {
  if (window.monaco) return window.monaco;
  await PluginLoader.load('monaco');
  return new Promise((resolve, reject) => {
    require.config({ paths: { 'vs': 'https://cdnjs.cloudflare.com/ajax/libs/monaco-editor/0.52.0/min/vs' }});
    window.MonacoEnvironment = {
      getWorker: () => new Worker(URL.createObjectURL(new Blob([/* workerMain */], { type:'application/javascript' })))
    };
    require(['vs/editor/editor.main'], () => resolve(window.monaco), reject);
  });
}

Qué hace este código:

  • Carga Monaco bajo demanda.
  • Configura workers para que el editor funcione bien en navegador.

5. Versiones 21–30: modo pro (UX + render/edición de formatos)

5.1 Resumen de prompts

  • Me centré “a saco” en el código porque es la parte con más chicha: estructura limpia, clases claras, y UX consistente.
  • Añadí soporte serio para Markdown, HTML, Python, JavaScript y ejemplos que prueban que todo renderiza bien.
  • La pelea grande fue visualizar y editar PDF/DOCX/ODT sin que se rompiera el layout ni el estado de edición.
  • Construí flujos: ver → editar → marcar “dirty” → guardar en navegador → reabrir sesión.
  • Detalles “pro”: paleta de comandos, atajos, drafts de ejemplo, zoom, toasts y “panic reset”.

6. Prompt maestro y metodología

6.1 Prompt inicial (preguntas hasta “PARA”)

Este fue el enfoque inicial: un prompt base + la regla de que la IA debía hacer preguntas hasta que yo dijera “PARA”, y entonces devolver un prompt final completo. (Pega aquí tu prompt real si quieres que quede 100% literal.)

Quiero que diseñes una aplicación web tipo “DocViewer / IDE” en un único HTML (HTML+CSS+JS).
Antes de proponer el prompt final, hazme preguntas una por una para concretar:
- Tipos de archivos soportados (md/html/pdf/docx/odt/xlsx…)
- Necesidades de edición, exportación y persistencia local
- UX: tabs, sidebar, atajos, command palette, tema dark/light, etc.

Regla: NO generes el prompt final hasta que yo diga explícitamente: “PARA”.
Cuando diga “PARA”, devuélveme:
1) Un prompt completo y ordenado
2) Una checklist de funcionalidades
3) Una lista de riesgos (pérdida de contexto, librerías, rendimiento) y mitigaciones.

6.2 Cómo lo usé por ciclos (mini-prompts)

  • Probé con Codex usando prompts grandes, pero el resultado estético no me convencía y el contexto se rompía.
  • Convertí el chat (Q&A) en un esquema de funcionalidades y lo usé como checklist externa.
  • Me di cuenta de que los mega-prompts eran el origen del caos: preferí muchos prompts pequeños y concretos.
  • Cuando encontré una estética base buena (Gemini), me quedé ahí y trabajé “a bisturí”: pequeños cambios, pruebas y mejoras de UX.
  • El enfoque final fue: profesionalizar el código + soporte serio de formatos + experiencia de usuario impecable.

7. Mapa rápido del código

Para localizarlo todo sin perderte (todo vive en un único HTML):

  • UI base (layout + tema) → <style> (variables :root, #app-shell, .workspace, .tab…)
  • Carga de librerías → PluginLoader
  • Persistencia IndexedDB → FileSystem
  • Visores/editores por formato → EditorFactory
  • Modales, command palette, toasts → UIManager
  • App state (tabs, active, session, save) → App
  • Configuración (fuente, panic reset) → SettingsManager
  • Run cloud compile → CompilerService (Piston)

Punto de entrada (inicio de la app):

window.App = App;
window.UIManager = UIManager;
window.SettingsManager = SettingsManager;

// App.instance crea el singleton al primer acceso y restaura sesión
static get instance() {
  if(!window.__app) window.__app = new App();
  return window.__app;
}

Un DocViewer/IDE local con experiencia “pro”: edición de Markdown/HTML/código, visores para PDF/DOCX/ODT, persistencia y detalles de UX (comandos, atajos, drafts, zoom).
